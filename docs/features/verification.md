# ブラウザでの改ざん検証

証明書の記録データが、Sepoliaに刻まれたハッシュと一致するかをブラウザ自身が確かめる機能。関連要件はFR-08、FR-09、FR-10、NFR-03。ブラウザで行う理由は [decisions/0001](../decisions/0001-verify-in-browser.md)。

## 検証の流れ

1. Goから記録データ本体と、各記録のトランザクションハッシュを取得する
2. ブラウザで記録データを正規化し、Web Crypto APIでSHA-256を計算する
3. SepoliaのRPC経由で、チェーン上に記録されたハッシュと時刻を読む
4. 一致・不一致・照合できずを区別して表示する

検証は概要画面と詳細画面の表示後に非同期で走らせ、ページの表示を待たせない（NFR-02）。

## 結果の状態

| 状態 | 条件 | 表示 |
| --- | --- | --- |
| 一致 | すべての記録のハッシュがチェーン上の値と一致 | 概要画面と詳細画面では「一致：改ざんなし」のバッジだけ。一致した記録数と照合日時は検証の詳細画面に出す |
| 不一致 | 1件でも一致しない記録がある | 概要画面では信用しないよう伝え、詳細画面ではどの記録が一致しなかったかを示す。/about の説明へ誘導 |
| 照合できず | APIやRPCの通信失敗、タイムアウト | 再試行ボタン。「不一致」と同じ見た目にしない |

## アプリ・Goとの取り決め

ここがずれると、正しいデータでもブラウザ検証が必ず「不一致」になる。3者で一字一句そろえる。

1. ハッシュ対象と正規化方式：記録データのJSONをRFC 8785（JCS）で正規化し、SHA-256を取る（案）。Kotlin・Go・ブラウザで同じ値になるか、テストベクタで確かめる
2. オンチェーン記録の形式：コントラクトのイベントで記録するか、トランザクションのデータ欄に載せるか。コントラクトアドレスとABIをWebに共有してもらう
3. 記録の粒度：記録1件ごとにトランザクションを送ると、検証時に記録数だけチェーンを照会することになる。発行時に全記録をまとめたマークルルート1件を刻む方式なら照会は1回で済む（要相談）

## テストベクタ

3者で同じファイルを共有し、それぞれのテストで読み込む（置き場所は要相談）。

```json
[
  {
    "name": "最小の記録",
    "input": { "recordedAt": "2026-10-01T00:00:00Z", "batteryCycleCount": 120 },
    "canonical": "{\"batteryCycleCount\":120,\"recordedAt\":\"2026-10-01T00:00:00Z\"}",
    "sha256": "fa32067d529aa8b9d464b7107bcc75724b74fcecd3d87b890a30ea423e4e8c8c"
  }
]
```

フィールド名は例。正式な名前はGoのスキーマに合わせる。正規化やハッシュの方式を変えるときは、このファイルと本書を同時に更新してアプリ・Go担当に共有する。

## 表示上の注意

- Sepoliaはテストネットであることを明記する
- 「一致」は記録後に改ざんされていないことを示すだけで、計測値の正しさまでは示さない。線引きは [security.md](../security.md) の信頼モデルに合わせる
- 検証の詳細画面（`/c/[ID]/verify`）では、記録ごとにハッシュ・トランザクションハッシュ・記録時刻とEtherscan（Sepolia）へのリンクを出す（FR-09）
- 正規化済みJSONをダウンロードでき、第三者が自分で検証できるようにする（FR-10）
